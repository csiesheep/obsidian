## Overview

一張台灣地圖,畫出四類連鎖店(便利商店、飲料店、速食店、賣場)的門市,點下去看到該品牌**現在有效**的優惠:名稱、起訖日、原始連結。優惠每天自動更新,過期自動下架。

一句話:**「我附近哪一家今天有活動?」** 打開手機就知道,點連結回官網看細節。

這不是比價網,也不是優惠券網。我們只放「標題+日期+連結」這種事實,細節一律導回品牌官網。

## 1. 目標與非目標(v1)

**目標**

1. 地圖上看得到 v1 品牌的門市點,手機上順暢(1.4 萬個點要能縮放、群聚)。
2. 每個品牌顯示「今天有效」的品牌層級優惠:標題、起訖日、適用範圍、來源連結、資料抓取時間。
3. 每天自動抓;任何一個來源壞掉,地圖上那個品牌保留上次的好資料並標「資料日期」,其他品牌照常。
4. 篩選:分類、品牌、「現在有優惠」。
5. 有一頁「資料狀態」:每個來源最後成功的時間、這次抓到幾筆。

**非目標(v1 不做)**

- 單一門市的庫存、價格、單店活動(加盟店自己的活動)。
- DM 裡的商品價格:不做 PDF/圖片 OCR。賣場只放「本期 DM 期間+連結」。
- App 內會員券、LINE 好友券、輸入代碼券(肯德基代碼、達美樂代碼)。
- FB/Threads/IG 的貼文(CoCo、得正、50嵐)。
- 使用者帳號、收藏、推播、投稿。
- 第三方整理站(myEDM、今購百科、新聞稿)的內容轉載。只在 v2 考慮「連過去」,不抓內容。

## 2. v1 品牌與理由

**選入條件**(四個都要滿足):

1. 官方頁面上就有優惠的**標題和日期**,不用登入、不用 App。
2. robots.txt 沒有禁止我們要抓的路徑。
3. 門市位置有可行的來源(開放資料、官網 HTML,或少到可以手動整理)。
4. 2026-10-02 從台灣網路實測回 200。

**v1 共 12 個品牌**

**為什麼這樣選**

- 便利商店是地圖的骨架:點最多、使用者最常找。7-11、全家、OK 三家的優惠來源都是「高」或「中」;萊爾富主站擋爬蟲,子站可以抓但門市要從 ASP.NET 表單拆,放 v2。
- 飲料店挑「官網有新聞頁、效期寫清楚、門市頁有地址或座標」的。清心福全、50嵐門數最多但一個更新慢、一個連不上,v1 不收。
- 速食只有必勝客和 21 世紀符合四個條件。麥當勞今天仍回 403。

**從研究建議名單拿掉的兩家,與原因(今天新查到)**

- **頂呱呱**:`tkkinc.com.tw/robots.txt` 整份只有一行 `disallow: *`。沒有 User-agent 行,依 RFC 9309 嚴格說是無效群組,但意圖很清楚是「不要抓」。v1 不自動抓;要收就寫信取得同意,或由人每兩週手動輸入一次。
- **好市多**:研究評「高」是因為商品頁 HTML 有價格,但 v1 不做商品價格。官網首頁是 Angular 單頁應用(2.2 MB),「本期特價」要找它的 API 才抓得到期間。門市 14 家很好手動整理。改列 v1.5:先確認有沒有乾淨的期間來源。

**7-11 的兩組日期**(今天實測發現,研究沒寫)

XML 每筆有 `SDate`/`EDate`(上架期間)和 `<Period>`(活動期間的文字)。例:「1010購物節」`SDate=20260901`、`EDate=20261011`,但 `Period` 是 `2026/10/7~10/11`。若用 `SDate` 顯示,9 月就會說「有優惠」而活動其實還沒開始。規則:**能解析 `Period` 就用 `Period`;解析不了才退回 `SDate/EDate`,並標「上架期間」**。這種「來源有兩組日期」的情況其他品牌也會有,資料模型要留位置(見第 3 節 `date_basis`)。

## 3. 資料模型

四張表。v1 量很小(門市約 1.5 萬、優惠約 100 筆),用一個 SQLite(Cloudflare D1)就夠。

### brands

| 欄位 | 說明 |
| --- | --- |
| `id` | `seven`, `family`, `okmart`, `starbucks`… |
| `name` | 顯示名(萬家福這種改名的,在這裡改,不動 id) |
| `category` | `cvs` 便利商店 / `drink` 飲料 / `fastfood` 速食 / `mart` 賣場 |
| `color` | 地圖點的顏色(不用品牌 logo,見第 7 節) |
| `home_url`, `promo_url` | 給使用者點的官方頁 |
| `enabled` | 下架一個品牌只改這一格 |

### stores

| 欄位 | 說明 |
| --- | --- |
| `id` | `<brand>:<來源內的 ID>`;商工資料用分公司統一編號 |
| `brand_id` | |
| `name` | 門市名。**商工資料沒有門市名**,只有「台北市第三七八分公司」,這時顯示品牌名+地址 |
| `address_raw`, `address_norm` | 原文與正規化後(全形轉半形、「二七一號」轉「271號」、去樓層) |

| `source`, `source_id` | 這筆從哪個資料集來 |
| `status` | `open` / `closed`;商工資料 `01` 才算 open,`03` 廢止、`06` 撤銷不畫 |
| `first_seen`, `last_seen` | 連續兩次月更新都沒出現就標 closed |

### offers

| 欄位 | 說明 |
| --- | --- |
| `id` | `<brand>:<來源內的 ID 或 hash(標題+起日)>`,讓每天重抓是 upsert 不是重複新增 |
| `brand_id` | |
| `title` | 原文標題,不改寫、不加料 |
| `start_date`, `end_date` | `YYYY-MM-DD`,台北時區;`end_date` 可為空 |
| `date_basis` | `event`(活動期間)/ `listing`(上架期間)/ `published`(只有公告日)/ `none` |
| `scope` | `all`(全門市)/ `some`(部分門市)/ `channel`(只限外送、App、LINE Pay 等) |
| `scope_note` | 例:「LINE Pay 付款」「外帶」「會員」;抓得到就填,抓不到留空 |
| `kind` | `discount` / `dm`(本期 DM)/ `new_item`(新品,v1 不顯示)/ `other` |
| `source_url` | 點過去看細節的官方網址 |
| `fetched_at` | 這筆最後一次在來源上看到的時間 |
| `first_seen_at` | 第一次看到 |
| `gone_at` | 來源**抓取成功**但這筆不見了的時間 |

### fetch_runs

| 欄位 | 說明 |
| --- | --- |
| `source_id`, `started_at`, `ok`, `http_status`, `items`, `error`, `sha256` | 每次抓取一列;`sha256` 是原始回應的雜湊,用來判斷「頁面沒變」 |

### 過期怎麼下架

顯示條件只有一條,在讀的時候算,不靠刪資料:

```
今天(台北) >= start_date
且 (end_date 為空 或 今天 <= end_date)
且 gone_at 為空
且 kind != new_item
```

- **有迄日**:過了迄日自動消失。
- **沒有迄日**(茶之魔手、COMEBUY 這類):顯示「未標迄日」,`first_seen_at` 起 30 天後自動隱藏,除非來源上還看得到它而且是今年的公告。30 天是猜的,上線後看資料再調。
- **來源成功、但這筆不見了**:填 `gone_at`,馬上隱藏(提早結束)。
- **來源失敗**:什麼都不動。`gone_at` 只在抓取成功時才會被設,所以壞掉的來源不會把優惠清空。

舊資料不刪,留著可以回頭看「這個品牌一年辦幾次活動」。

## 4. 抓取(ingestion)

### 一個來源一個小抓取器

每個抓取器只做一件事:給它原始回應,吐出統一格式。

```
fetch(source)  -> 原始回應(存一份到 R2,按日期)
parse(raw)     -> [{ title, start_date, end_date, date_basis, scope, scope_note, kind, source_url, source_item_id }]
```

`parse` 是純函式、不碰網路,所以可以拿存下來的原始回應測。共用的部分(抓網頁、民國年/西元年/「10/7~10/11」這類日期解析、寫資料庫、健康檢查)只寫一次。

### 排程

- 優惠:每天一次,台北時間 06:00。每個來源一個請求(少數要再進內頁的,每天最多 10 個),請求之間隔 5 秒。
- 門市:每月一次。商工資料每月更新,抓 CSV、比對差異、只對新增或地址變更的做地理編碼。
- 前端讀的是每天產生一次的靜態快照(見第 6 節),所以使用者再多也不會多打來源網站一次。

### 一個來源壞掉不能讓地圖空白

1. **每個來源獨立跑**,一個丟例外不影響別的。
2. **抓到 0 筆、或解析出錯、或筆數比上次少一半以上**:視為失敗,不寫入 `offers`,保留上次的資料。
3. **快照永遠用每個品牌「最後一次成功」的資料組**。前端在品牌旁顯示「資料日期 10/02」;超過 3 天沒成功變灰字「資料可能過期」。
4. 連續失敗 2 天,通知 owner(email 或 Discord webhook,owner 選)。

### 怎麼知道抓取器還正常

三層:

- **固定樣本測試**:每個來源存 2–3 份真實回應當 fixture,`parse` 結果要等於預期。改程式時跑。
- **每日健全檢查**:每筆日期要解析得出來、`end >= start`、起日不晚於今天 + 60 天、標題不是空的也不是整頁的導覽文字。不過就算失敗。
- **每週抽查**:「資料狀態」頁列出每個品牌今天抓到的標題;owner 或一個排程 agent 每週對照官網看一次。這一步抓得到「解析沒錯但抓錯區塊」這種健全檢查看不出來的錯。

**要警惕的假綠燈**:頁面改版後抓取器可能抓到別的區塊(例如「最新消息」變成「新品上市」),筆數照樣 > 0、日期照樣能解析。所以每個抓取器要有一條「這個來源**一定**有的特徵」的檢查(7-11:XML 根節點是 `<BD>`;必勝客:至少一筆 `type=cb`;OK:頁面有「活動日期:」字樣),特徵不見就算失敗。

## 6. 前端與部署

### 畫面(手機優先)

- 全螢幕地圖,上方一排分類膠囊(便利/飲料/速食/賣場),一個「現在有優惠」開關,一個品牌多選(底部抽屜)。
- 點群聚放大;點門市跳出底部卡片:品牌、地址、該品牌今天有效的優惠(標題、起訖日、範圍、「看官網」連結)、「資料日期」。
- 第二個分頁「優惠列表」:不看地圖,直接按品牌列出今天有效的優惠。很多人其實只要這頁。
- 「定位我」按鈕(瀏覽器定位,不存、不上傳)。
- 頁尾:資料來源與顯名、免責聲明、「資料狀態」連結。
- 依 owner 在真 iPhone 上測的經驗:高度用 `svh`,不要全域 `min-height: 100vh`,在真的 iPhone 上驗。

### 地圖

- **MapLibre GL** + 台灣範圍的 **Protomaps PMTiles** 放在 R2。不靠第三方圖磚服務、沒有 API 金鑰、沒有用量帳單;要標 OpenStreetMap 貢獻者。
- 1.4 萬個點用 MapLibre 內建 cluster,一份 GeoJSON(gzip 後估 300–500 KB)。太大再按分類切檔。

### 資料流

```
Cron(每天 06:00) → 抓取器 → D1(offers、fetch_runs)+ R2(原始回應)
                         ↓
                   產生快照 offers.json、stores-<category>.geojson → R2
                         ↓
前端只讀快照(Cloudflare 快取 1 小時)
```

### 放哪裡

games.csiesheep.com 的架構是:一個 `games` Worker 拿 Custom Domain 當大廳,每個遊戲是獨立的 Worker,用 `games.csiesheep.com/<slug>/*` 路由切走。技術上可以把這個掛成 `/discount/`。

**建議開自己的子網域**,例如 `deals.csiesheep.com`(名字 owner 定):

- 它不是遊戲。放在遊戲大廳下面,分享連結時很奇怪,大廳也要決定要不要列它。
- 它有 Cron、D1、R2,和遊戲的部署節奏無關。分開的 Worker 出事不會碰到遊戲。
- 它的法律頁、顯名、免責聲明是自己的。

**需要的東西**(都在 owner 現有的 Cloudflare 帳號裡):

1. 一個新 Worker,`routes` 用 `{ "pattern": "deals.csiesheep.com", "custom_domain": true }`(和 `games` Worker 同樣做法)。
2. `triggers.crons`:每天一次、每月一次。
3. 一個 D1 資料庫、一個 R2 bucket(快照、原始回應、PMTiles)。
4. 用量:每天幾十個外部請求、一次快照產生,免費額度內。R2 存 PMTiles 台灣範圍估數十到一兩百 MB,也在免費額度內。
5. 上線前 `noindex`,和遊戲一樣等 owner 說 go 才開放索引。

**一個要先驗的風險**:我今天所有實測都是從 owner 的電腦(台灣住家網路)打的。Cloudflare Worker 的對外 IP 是 Cloudflare 的、而且 Cron 不一定在台灣機房跑,有些台灣網站會擋海外或機房 IP(研究裡摩斯、拿坡里可能就是這樣)。**Phase 0 第一件事:從 Worker 對 12 個來源各打一次,記下回應碼**。不通的來源,備案依序是:換抓取時間、經由 owner 的機器抓(但那台電腦不穩定,不能當主力)、放棄該來源。

## 7. 法律與使用條款

1. **robots.txt**:每個來源上線前讀一次並記在抓取器裡;每週自動重讀,有變就停抓並通知。
   - 7-11:`Disallow: *.xml*`。我們打的 `/readxml.aspx` 不含 `.xml`,字面上沒被禁;但頁面註解裡提到的 `/include/SalesPromo.xml` 是被禁的,**我們不碰那個檔**。這是灰色地帶,owner 要決定能不能接受(或寫信問)。
   - 頂呱呱:`disallow: *`,v1 不抓。
   - 星巴克只禁 `/starbuckschannel/`,路易莎全開,其他幾家沒有 robots.txt。
2. **頻率與身分**:每天每來源 1 次;User-Agent 寫明網站名稱與聯絡網址。被要求停止就停。
3. **只放事實,不轉載內容**:標題、日期、連結。不抓圖片、不複製活動說明文字、不放品牌 logo(用色點和文字)。OK mart 頁尾寫「轉載必究」,這個做法就是為這種條款準備的。
4. **連回官方**:每筆優惠都連回品牌自己的頁面,我們是索引,不是替代品。
5. **第三方整理站**(myEDM、今購百科、新聞):不抓、不轉載。myEDM 的 robots 是開的,但 robots 開放不等於授權轉載;v2 若要用,先寫信取得同意。
6. **開放資料顯名**:商工資料「提供機關/經濟部商業發展署」;地圖「© OpenStreetMap contributors」;TGOS 若有要求一併標。
7. **免責聲明**:「優惠內容以各品牌官方公告為準;部分門市不適用;本站與各品牌無關。」
8. **商標**:品牌名用文字介紹性使用;不用 logo、不仿品牌配色當主視覺。

## 8. 風險與待確認

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| Worker IP 被來源擋 | 該品牌沒資料 | Phase 0 先測;見第 6 節備案 |
| 頁面改版,抓取器抓錯區塊卻不報錯 | 顯示錯的優惠 | 「一定有的特徵」檢查+每週抽查 |
| 日期語意不一(上架期間 vs 活動期間;只有公告日) | 太早或太晚顯示 | `date_basis` 欄位;不確定就標出來而不是猜 |
| 加盟店不配合品牌活動 | 使用者到店撲空 | `scope` 欄位;卡片上永遠寫「部分門市可能不適用」 |
| 商工資料涵蓋不全(全家缺兩成、OK 缺七成) | 地圖點不完整 | OK 用官網;全家先接受,頁面註明 |
| TGOS 不收個人申請 | 地理編碼要另想 | 先問;備案用批次比對服務一次做完 |
| 品牌改名、併購(家樂福→萬家福/樂家康、大潤發→大全聯) | 名字過時 | 只改 `brands.name`;每季人工看一次 |

| 被品牌要求停止 | 少一個品牌 | 一鍵 `enabled=false`;尊重 |
