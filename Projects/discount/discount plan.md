## Overview

一張台灣地圖,畫出四類連鎖店(便利商店、飲料店、速食店、賣場)的門市,點下去看到該品牌**現在有效**的優惠:名稱、起訖日、原始連結。優惠每天自動更新,過期自動下架。

一句話:**「我附近哪一家今天有活動?」** 打開手機就知道,點連結回官網看細節。

這不是比價網,也不是優惠券網。我們只放「標題+日期+連結」這種事實,細節一律導回品牌官網。

## 1. 目標與非目標(v1)

**目標**

1. 地圖上看得到 v1 品牌的門市點,手機上順暢(1.4 萬個點要能縮放、群聚)。
2. 每個品牌顯示「今天有效」的品牌層級優惠:標題、起訖日、適用範圍、來源連結、資料抓取時間。
3. 每天自動抓;任何一個來源壞掉,地圖上那個品牌保留上次的好資料並標「資料日期」,其他品牌照常。
4. 篩選:分類、品牌、「現在有優惠」。
5. 有一頁「資料狀態」:每個來源最後成功的時間、這次抓到幾筆。

**非目標(v1 不做)**

- 單一門市的庫存、價格、單店活動(加盟店自己的活動)。
- DM 裡的商品價格:不做 PDF/圖片 OCR。賣場只放「本期 DM 期間+連結」。
- App 內會員券、LINE 好友券、輸入代碼券(肯德基代碼、達美樂代碼)。
- FB/Threads/IG 的貼文(CoCo、得正、50嵐)。
- 使用者帳號、收藏、推播、投稿。
- 第三方整理站(myEDM、今購百科、新聞稿)的內容轉載。只在 v2 考慮「連過去」,不抓內容。

**為什麼這樣選**

- 便利商店是地圖的骨架:點最多、使用者最常找。四大超商全收:7-11、OK 的優惠來源是「高」,全家、萊爾富是「中」(萊爾富只能抓子站)。萊爾富門市用商工資料就有八成五,不必拆官網的 ASP.NET 表單。
- 飲料店挑「官網有新聞頁、效期寫清楚、門市頁有地址或座標」的。清心福全、50嵐門數最多但一個更新慢、一個連不上,v1 不收。
- 速食只有必勝客和 21 世紀符合四個條件。麥當勞今天仍回 403。

**從研究建議名單拿掉的兩家,與原因(今天新查到)**

- **頂呱呱**:`tkkinc.com.tw/robots.txt` 整份只有一行 `disallow: *`。沒有 User-agent 行,依 RFC 9309 嚴格說是無效群組,但意圖很清楚是「不要抓」。**owner 決定不收**(2026-10-08),v2 也不收。
- **好市多**:研究評「高」是因為商品頁 HTML 有價格,但 v1 不做商品價格。官網首頁是 Angular 單頁應用(2.2 MB),「本期特價」要找它的 API 才抓得到期間。門市 14 家很好手動整理。改列 v1.5:先確認有沒有乾淨的期間來源。

**7-11 的兩組日期**(今天實測發現,研究沒寫)

XML 每筆有 `SDate`/`EDate`(上架期間)和 `<Period>`(活動期間的文字)。例:「1010購物節」`SDate=20260901`、`EDate=20261011`,但 `Period` 是 `2026/10/7~10/11`。若用 `SDate` 顯示,9 月就會說「有優惠」而活動其實還沒開始。規則:**能解析 `Period` 就用 `Period`;解析不了才退回 `SDate/EDate`,並標「上架期間」**。這種「來源有兩組日期」的情況其他品牌也會有,資料模型要留位置(見第 3 節 `date_basis`)。

### 過期怎麼下架

顯示條件只有一條,在讀的時候算,不靠刪資料:

```
今天(台北) >= start_date
且 (end_date 為空 或 今天 <= end_date)
且 gone_at 為空
且 kind != new_item
```

「現在有優惠」篩選再多一條:`scope != channel`。LINE Pay、信用卡、外送平台、App 限定的活動不算「有優惠」(owner 2026-10-08)。它們仍然列在品牌卡片和列表頁,但收在「付款/通路限定」小標下,預設收合。所以抓取器判斷 `scope` 要保守:標題含 LINE Pay、街口、信用卡、Uber Eats、foodpanda、App、會員限定等字樣就標 `channel`。

- **有迄日**:過了迄日自動消失。
- **沒有迄日**(茶之魔手、COMEBUY 這類):顯示「未標迄日」,`first_seen_at` 起 30 天後自動隱藏(owner 2026-10-08 同意)。就算來源上還掛著也一樣隱藏;上線後看資料再決定要不要調。
- **來源成功、但這筆不見了**:填 `gone_at`,馬上隱藏(提早結束)。
- **來源失敗**:什麼都不動。`gone_at` 只在抓取成功時才會被設,所以壞掉的來源不會把優惠清空。

舊資料不刪,留著可以回頭看「這個品牌一年辦幾次活動」。

## 4. 抓取(ingestion)

### 一個來源一個小抓取器

每個抓取器只做一件事:給它原始回應,吐出統一格式。

```
fetch(source)  -> 原始回應(存一份到 R2,按日期)
parse(raw)     -> [{ title, start_date, end_date, date_basis, scope, scope_note, kind, source_url, source_item_id }]
```

`parse` 是純函式、不碰網路,所以可以拿存下來的原始回應測。共用的部分(抓網頁、民國年/西元年/「10/7~10/11」這類日期解析、寫資料庫、健康檢查)只寫一次。

### 排程

- 優惠:每天一次,台北時間 06:00。每個來源一個請求(少數要再進內頁的,每天最多 10 個),請求之間隔 5 秒。
- 門市:每月一次。商工資料每月更新,抓 CSV、比對差異、只對新增或地址變更的做地理編碼。
- 前端讀的是每天產生一次的靜態快照(見第 6 節),所以使用者再多也不會多打來源網站一次。

### 一個來源壞掉不能讓地圖空白

1. **每個來源獨立跑**,一個丟例外不影響別的。
2. **抓到 0 筆、或解析出錯、或筆數比上次少一半以上**:視為失敗,不寫入 `offers`,保留上次的資料。
3. **快照永遠用每個品牌「最後一次成功」的資料組**。前端在品牌旁顯示「資料日期 10/02」;超過 3 天沒成功變灰字「資料可能過期」。
4. 連續失敗 2 天,寄 email 給 owner(csiegoat@gmail.com)。一天最多一封摘要信,列出所有失敗的來源,不要一個來源一封。寄信用 Cloudflare Email Routing 的 Worker 寄件(收件地址要先在 Cloudflare 驗證),或外部寄信服務;Phase 0 選一個。

### 怎麼知道抓取器還正常

三層:

- **固定樣本測試**:每個來源存 2–3 份真實回應當 fixture,`parse` 結果要等於預期。改程式時跑。
- **每日健全檢查**:每筆日期要解析得出來、`end >= start`、起日不晚於今天 + 60 天、標題不是空的也不是整頁的導覽文字。不過就算失敗。
- **每週抽查**:「資料狀態」頁列出每個品牌今天抓到的標題;owner 或一個排程 agent 每週對照官網看一次。這一步抓得到「解析沒錯但抓錯區塊」這種健全檢查看不出來的錯。

**要警惕的假綠燈**:頁面改版後抓取器可能抓到別的區塊(例如「最新消息」變成「新品上市」),筆數照樣 > 0、日期照樣能解析。所以每個抓取器要有一條「這個來源**一定**有的特徵」的檢查(7-11:XML 根節點是 `<BD>`;必勝客:至少一筆 `type=cb`;OK:頁面有「活動日期:」字樣),特徵不見就算失敗。

### 放哪裡

games.csiesheep.com 的架構是:一個 `games` Worker 拿 Custom Domain 當大廳,每個遊戲是獨立的 Worker,用 `games.csiesheep.com/<slug>/*` 路由切走。技術上可以把這個掛成 `/discount/`。

**決定:`discount.csiesheep.com`,自己的子網域**(owner 2026-10-08)。理由:

- 它不是遊戲。放在遊戲大廳下面,分享連結時很奇怪,大廳也要決定要不要列它。
- 它有 Cron、D1、R2,和遊戲的部署節奏無關。分開的 Worker 出事不會碰到遊戲。
- 它的法律頁、顯名、免責聲明是自己的。

**需要的東西**(都在 owner 現有的 Cloudflare 帳號裡):

1. 一個新 Worker,`routes` 用 `{ "pattern": "discount.csiesheep.com", "custom_domain": true }`(和 `games` Worker 同樣做法)。
2. `triggers.crons`:每天一次、每月一次。
3. 一個 D1 資料庫、一個 R2 bucket(快照、原始回應、PMTiles)。
4. 用量:每天幾十個外部請求、一次快照產生,免費額度內。R2 存 PMTiles 台灣範圍估數十到一兩百 MB,也在免費額度內。
5. 開發期間 `noindex`;因為要對外公開,owner 說 go 後拿掉 `noindex`、送 sitemap。上線前第 7 節的法律頁、顯名、聯絡方式要先做好。
6. 對外公開代表會有陌生流量:前端只讀 R2 快照、全部走 Cloudflare 快取,使用者再多也不會多打來源網站。不放追蹤程式;要看流量用 Cloudflare 內建的 Web Analytics(不設 cookie)。

**一個要先驗的風險**:我所有實測都是從 owner 的電腦(台灣住家網路)打的。Cloudflare Worker 的對外 IP 是 Cloudflare 的、而且 Cron 不一定在台灣機房跑,有些台灣網站會擋海外或機房 IP(研究裡摩斯、拿坡里可能就是這樣)。**Phase 0 第一件事:從 Worker 對 13 個來源各打一次,記下回應碼**。不通的來源,備案依序是:換抓取時間、經由 owner 的機器抓(但那台電腦不穩定,不能當主力)、放棄該來源。
