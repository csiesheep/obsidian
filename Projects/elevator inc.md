## 四、電梯公司：詳細設計

### 4.1 為什麼這個點子好

三個結構性優勢：

1. **進度軸就是收入軸。** 樓層數同時是「你走多遠了」和「你賺多少錢」。大多數增量遊戲得硬把這兩件事綁在一起（Dirt Clicker 的地層得額外配掉寶表才有意義），電梯天生就綁好了：票價 = 樓層差。
2. **張力是內建的，不是外掛的。** 樓越高，單趟收入越高，但**往返時間也越長**，低樓層乘客等到不耐煩就走人。這不是設計師硬塞的限制器（像體力條），而是從題材本身長出來的兩難。這種張力玩家會覺得公平。
3. **視覺天生適合手機直式。** 垂直捲動的井道剖面填滿螢幕，往上蓋的時候相機拉遠、樓變成一根細長的塔——這個「看著自己蓋的東西變高」的畫面本身就是獎勵。

### 4.2 核心循環

```
乘客在某樓生成（有目的地、耐性條）
  → 玩家/演算法決定電梯下一站
    → 電梯移動（加速 → 巡航 → 減速）
      → 開門、上下客
        → 收入 = 基礎票價 × |樓層差| × 乘客倍率 × 滿意度乘數
          → 花錢升級 → 樓變高 → 流量變大 → 回到開頭
```

### 4.3 核心動詞：手動調度

早期完全手動。畫面上顯示各樓等待中的小人偶（頭上有目的地標籤），玩家**點擊要去的樓層**來調度電梯。

這比純點擊有腦，因為玩家實際上在做取捨：先接 3 樓那三個上班族（近、便宜、快沒耐性），還是衝去 28 樓接那個 CEO（遠、超高單價、耐性極低）？

而且自動化的路徑非常乾淨：你買的不是「自動點擊器」，是**更好的調度演算法**。

### 4.4 體力的對應物：馬達過熱

按住空白鍵／長按讓電梯超速行駛（1.8×），但熱量累積。過熱就強制停機冷卻 8 秒，期間所有乘客耐性照跑。

這給了主動遊玩一個持續的、有風險的操作，對應 Bills Must Be Paid 的體力機制，但不會硬性結束一局。升級路線：散熱片 → 液冷 → 超導馬達（過熱機制最終被移除，這本身就是一個爽的里程碑）。

### 4.5 貨幣

| 貨幣 | 用途 | 是否跨 Prestige |
|---|---|---|
| **現金 $** | 一般升級：速度、載重、門、電梯井 | ✗ |
| **藍圖 📐** | 技能樹、樓層類型解鎖、地基等級 | ✓ |
| **評價 ★** | 不是貨幣，是**乘數**。滿意度累積成大樓評價，評價高 → 更高單價的租戶入住 → 所有票價 ×N | 部分保留 |

評價是這個設計的第二個聰明處：它讓「別讓乘客生氣」有長期複利價值，而不只是當下少賺一筆。

### 4.6 核心數值

電梯只有五個屬性，全部互相牽制：

| 屬性 | 影響 | 取捨 |
|---|---|---|
| 巡航速度 | 長程變快 | 對短程幾乎無幫助 |
| 加速度 | 短程變快 | 對長程幾乎無幫助 |
| 載客量 | 一趟載更多 | 但上下客時間變長 |
| 開關門時間 | 每站省秒數 | 站數多才有價值 |
| 電梯井數 | 平行處理 | 成本最貴，且需要調度演算法才發揮 |

**這五個屬性沒有一個是「全面更好」的**，所以升級選單永遠是真決策。這是 Bills Must Be Paid 的鎚子系統（高爆擊小範圍 vs. 高速大範圍低傷害）的同一招。

### 4.7 起始平衡（第一版）

```
起始狀態
  樓層數：10
  電梯井：1
  巡航速度：1.0 樓/秒
  加速度：0.5 樓/秒²
  載客量：4
  開關門：2.0 秒
  乘客生成：每 4 秒 1 位

經濟
  票價 = $1 × |樓層差| × 乘客倍率 × 評價乘數
  成本曲線 = base × 1.12^已購買數

前三個升級（教學用）
  +2 載客量        $50
  開關門 -0.4 秒    $80
  +5 層樓          $200   ← 第一次感受到「樓高 = 錢多」
```

第一次自動化（自動關門）應該在**遊玩約 6 分鐘**出現，第一個完整調度演算法在 **15 分鐘**。太晚玩家會累。

### 4.8 自動化階梯

這是遊戲的骨幹，也是最有梗的部分——因為電梯調度是**真實存在的電腦科學問題**：

1. **自動關門** — 最基本的解放
2. **FIFO 調度** — 誰先按誰先服務。笨，但你不用點了
3. **SCAN 演算法** — 電梯掃到頂再掃到底，不折返
4. **LOOK 演算法** — 掃到最遠請求就折返，不跑空段
5. **目的地控制（Destination Dispatch）** — 乘客在大廳先輸入目的地，系統分組。真實高樓技術
6. **群組控制** — 多井協同，不再各自為政
7. **快速電梯（Shuttle）** — 只停高樓層，不吃低樓流量
8. **雙層轎廂（Double-decker）** — 一次服務兩層
9. **空中大廳（Sky Lobby）** — 真實摩天樓設計，換乘節點，讓超高樓在數學上可行

玩家在解鎖第 3 個之後會發現：**這些演算法真的有效率差異**，而且遊戲有統計頁面能看出來（借 Dirt Clicker 的「誰在偷懶」）。

### 4.9 乘客類型（收集要素）

| 類型 | 票價 | 耐性 | 特性 |
|---|---|---|---|
| 上班族 | 低 | 低 | 量最大，尖峰時段暴增 |
| 觀光客 | 中 | 高 | 拍照，拖慢開門 2 秒 |
| 送貨員 | 高 | 中 | 佔 2 格空間 |
| 保全 | 無 | ∞ | 不付錢，但提升評價 |
| CEO | 極高 | 極低 | 要求專用電梯，讓他等會扣評價 |
| 貓 | 無 | 高 | 純提升評價。稀有 |
| 幽靈 | ??? | — | 只在 13 樓出現。稀有掉落 |
| 搬家公司 | 極高 | 低 | 塞滿整台電梯 |

目標約 20 種，配一本圖鑑。這是獨立於數字線之外的獎勵管道。

### 4.10 樓層類型（進度軸）

| 樓層 | 類型 | 解鎖的東西 |
|---|---|---|
| 1–10 | 零售 | 基礎流量 |
| 11–30 | 辦公 | 尖峰時段機制（早上 9 點暴衝） |
| 31–60 | 飯店 | 行李（載重機制）、夜間流量 |
| 61–100 | 住宅 | 常客、寵物 |
| 101–150 | 觀景台 | 觀光客潮 |
| 151+ | 實驗樓層 | 破壞平衡的東西 |
| 終局 | 屋頂 → 軌道 | 電梯衝出大氣層，遊戲結束 |

**結局很重要。** 參考的三款都是短遊戲，目標總時長 **4–6 小時**。

### 4.11 Prestige：打掉重蓋

觸發條件：蓋滿一定樓層或收入達標。

**保留**：藍圖、已解鎖樓層類型、乘客圖鑑、地基等級（= 新樓的基礎速度與最大高度）
**歸零**：現金、樓層數、所有現金升級

```
藍圖獲得量 ≈ floor( sqrt( 本輪總收入 / 1e6 ) )
```

主題上完美：拆一棟樓蓋更高的一棟，正是現實摩天樓的歷史。

技能樹三大分支：

- **機械**：速度、加速、載重、散熱
- **營運**：調度演算法、多井、群組控制
- **建築**：起始樓層、樓層類型、空中大廳

### 4.12 UI 與視覺

- **手機直式（主要）**：井道剖面填滿螢幕，升級用底部抽屜（swipe up）
- **桌機**：左側井道，右側升級面板
- 美術風格：扁平向量或像素，樓層有不同配色與家具剪影
- 乘客是小人偶，頭上有目的地數字標籤，耐性用頭頂細條表示（快沒耐性時變紅並晃動）
- **關鍵爽點**：每次增加樓層，相機平滑拉遠。玩到後期整棟樓縮成一根細塔，你能一眼看到自己蓋了多高
- 音效：叮！開門聲、樓層播報。這遊戲的音效設計空間很大且很便宜

### 4.13 技術注意事項

- 電梯運動是**簡單 1D 運動學**（等加速 → 巡航 → 等減速），不需要物理引擎。約 40 行程式碼
- 乘客是純物件陣列：`{ id, origin, dest, type, spawnTime, patience }`
- **最大的技術決策**：後期樓層數上百、乘客數上千，逐一模擬會爆。必須在中期切換成**統計流量模型**——高樓層不再逐個模擬乘客，改用「該區段每秒產生 N 元」的抽象。**這件事要在第 3 週前就決定好架構**，事後補很痛
- 離線收益：用平均流量 × 時間直接算，**不要重跑模擬**
- 存檔大小要注意：不要把乘客陣列存進 localStorage，只存統計數字

### 4.14 已知風險

| 風險 | 對策 |
|---|---|
| 手動調度太忙會累人 | 自動化提早，第一個演算法 15 分鐘內給 |
| 「進度軸就是錢」導致低樓層迅速失去價值，玩家只跑頂層 | 低樓層流量隨大樓高度**同步成長**（住戶都要經過大廳），並讓零售層有獨立的評價貢獻 |
| 五屬性互相牽制聽起來好，但可能算不出最佳解而讓玩家癱瘓 | 提供一個「效率」統計數字（每分鐘樓層數 × 載客率），讓玩家有可比較的單一指標 |
| 演算法梗太宅 | 每個演算法配一句白話說明 + 一個能看出差別的動畫示意 |

### 4.15 第一個原型該做什麼

**兩天內做完，只做這些：**

- 一個 10 層的井道，SVG 或 canvas
- 一部會動的電梯（加速度運動學）
- 點樓層 → 電梯過去 → 開門 → 上下客 → 加錢
- 乘客每 4 秒生成一個，頭上有目的地數字
- 一個計數器顯示 $

**驗證問題**：光是「點樓層、看電梯滑過去、叮一聲開門、錢跳出來」這件事，有沒有讓你想再點一次？

有的話，其他所有系統都值得做。沒有的話，問題在動詞的手感（速度曲線、音效、開門動畫），先修那個，不要急著加升級。

### 5.1 診斷：一行 clamp 造成的三個症狀

`js/sim.js` 的 `spawn()` 裡：

```js
const top = Math.min(st.floors, C.SIM_FLOORS);   // SIM_FLOORS = 40
```

| 症狀 | 原因 |
|---|---|
| 電梯永遠在低樓層往返 | 200 層的樓，**看得見的乘客只生成在 1–40 樓**，上面 160 層一個人都沒有 |
| 高樓層沒有客人 | 同上；4.13 的統計流量模型把他們變成了看不見的數字 |
| 蓋高樓沒有變忙 | `spawnEvery`（`js/state.js`）用同一個 clamp → **超過 40 樓之後人流不再增加** |

1–40 樓之內是**均勻分布**外加 15–45% 的大廳偏好，沒有任何真實建築的垂直人口結構。

這同時也是「後期沒事做」的根因：**後期的人全部住在玩家看不到的抽象模型裡。**

順帶量出來的平衡問題（2026-09-04）：

- 所有現金升級買滿只要 **約 $189 萬**，而後期收入約 **$336 萬/分** → 現金樹撐不到一分鐘
- 藍圖全樹＋全自動化只要 **471 📐**，一輪 100 億收入給 100 📐 → 約 5–8 次拆樓就全滿
- **整個遊戲沒有任何無上限的 sink**，每一項都有 max，而那些 max 相對後期收入小到可以忽略

### 5.2 人流與樓層：12 個點子

✅ = 這一輪選定實作。

**樓層分布**

**1. ✅ 取樣模擬（sampled simulation）** — 核心
高樓層不是不生成人，而是**只生成 5%，每個人身上帶 20 人份的票價**。畫面上高樓層有零星但高價的乘客，電梯有理由跑上去，CPU 仍是常數級。沒有推翻 4.13 的決定，只是把「不模擬」改成「抽樣」。
> 抽象收入要扣掉被取樣出去的那一部分，否則重複計算。

**2. ✅ 垂直人口分布（OD matrix）** — 丟掉 uniform
每個樓層帶有自己的起訖傾向：大廳約 40% 起訖、辦公層早上進晚上出、住宅層相反、飯店層夜間到達、觀景台單向朝聖。真實電梯交通研究就是用 OD matrix 算的，順便把行程長度拉開。

**3. 手扶梯／低區獨立電梯**
花錢把 1–5 樓的人流從電梯移走（真實建築就是這樣做的）。**用錢買清淨**，買下去之後剩下的都是長程高價客。同時是後期的現金 sink。

**4. 空中大廳變成真的轉運點**
現在 sky lobby 只是個倍率。改成真的兩段式行程：低區車只到大廳，高區車從大廳往上。高樓層自然有車在跑，而且「換乘」本身是新的調度難題。

**5. 頂樓吸引子**
觀景台／婚宴廳／直升機坪＝目的地磁鐵，製造穩定的長程高價流。13 樓的幽靈已證明「某層有特別的東西」很有記憶點。

**6. ✅ 解除 `spawnEvery` 的 clamp**
用真實樓數而不是 `min(floors, 40)`，人流才會隨大樓成長。
> 單獨做這條會直接把低樓層淹掉，**必須跟 1 一起做**。

**客人數量**

**7. ✅ Poisson + 「今日人潮」隨機遊走**
現在是固定間隔的節拍器。改成 Poisson 分布，再乘一條緩慢隨機遊走的日係數。平均值一樣，體感天差地遠——有忙到爆的時候，也有喘息的時候。投報率最高的一條。

**8. ✅ 突發流量事件**
會議散場、火警演習、演唱會散場、跨年倒數：一次在同一層丟出 20 個人。這是唯一會讓玩家「啊糟糕」然後手動接管的東西，也是後期還會主動玩的理由。

**9. ✅ 一週作息**
平日／週末不同曲線，而且飯店層與辦公層**相反**。一天 3 分鐘 → 一週 21 分鐘，剛好是一個 session 的長度。

**10. 入住率（Occupancy）**
樓蓋好不等於有人，要花錢招商。同時解決三件事：高樓層為什麼沒人、現金沒有 sink、以及「蓋新的 vs 填滿舊的」變成決策。

**11. 口碑迴圈**
評價目前只影響票價。讓它也影響**人數**：高評價 → 更多人 → 更忙 → 更容易失控。評價變成真正的雙面刃。

**12. 天氣與災害**
颱風天人少但耐性差；停電只剩一台能跑；地震後全部停機檢查。讓多買的那幾座井有「冗餘」的意義。

### 5.3 後期成長：15 個點子

後期真正缺的不是數字，是「有事情要決定」。純粹再加「+5% 速度」只會讓一個沒有互動的畫面數字變大。

**A. 止血（純資料改動，最快）**

1. **Mk II 無限升級** — 買滿的升級轉成無限等級版（+3% 乘法／級，成本成長 ×1.4）。現金終於有無底洞
2. **里程碑倍率** — 每 25 樓永久 ×1.15 收入，200 樓不再是一面平的牆
3. **藍圖來源多元化** — 成就、圖鑑集滿、每個樓層帶首次解鎖都給 📐，不要只靠 `sqrt(收入)` 一條管道
4. **評價開上限** — ★5 之後進入「聲望」，每 0.1 給票價加成，遞減但無上限

**B. 讓後期有決策（重點）**

5. **分區服務 Zoning** — 手動指定每座井的服務樓層區間（低／中／高區）。真實摩天樓就是這樣配的，而且樓每長高一段就要重解一次
6. **可調參數的調度器** — 把 dispatcher 的權重開成滑桿：等待時間 vs 距離 vs 票價 vs 耐性，統計頁即時顯示效率。**零內容成本、無限優化深度**，完全切中主題
7. **時段策略** — 早上上行尖峰、傍晚下行尖峰要用不同編組，真實電梯控制系統本來就有這個模式

**C. 把「五屬性互相牽制」在後期重新啟動**

8. **電力** — 每座井耗電，速度與加速是平方級耗電。買變電站、**再生制動**（下行發電，真實技術）。速度升級重新開始有代價
9. **保養與故障** — 磨損度累積、會故障停機；買預測性維護、備品倉。多買的井終於有冗餘的意義
10. **法規檢查** — 定期消防／無障礙／地震檢查，過不了扣評價。升級：消防員電梯模式、地震感測器

**D. 新的成長軸（工程量大）**

11. **地下樓層 B1～Bn** — 停車場、地鐵連通、金庫。往下蓋是另一條軸，有自己的乘客與風險（淹水）。「深海打撈」的張力可以整套搬過來
12. **第二棟樓／都市層** — 第二次 prestige，土地當第三貨幣，多棟樓的組合管理
13. **太空電梯** — 200 樓的結局不是結束而是換模式：軌道段用新貨幣（配重、纜線張力）。把結局變成第三章

**E. 讓圖鑑在後期有機械意義**

14. **電梯型號** — 每座井裝一台有屬性 profile 的機型，對應 Bills Must Be Paid 的鎚子系統（高速小容量 vs 慢速大容量）
15. **常客委託** — 圖鑑角色給任務（「送我到頂樓 20 次」）→ 永久 buff

**如果只做三件事**：1（無限升級，止血）＋ 6（可調調度器，後期唯一真正的腦力活動，也最便宜）＋ 8（電力，讓取捨回來）。
5 分區服務是最有味道的一個——真實工程問題，而且每個玩家想出來的解法會不一樣。

### 5.4 實作紀錄（2026-09-04）

六項全部做完，`js/content.js` / `sim.js` / `state.js` / `render.js` / `ui.js`。

**測試中抓到的兩個真問題**

1. **高樓層的乘客在物理上不可能被服務到。** 190 樓來回一趟要 190 秒，而上班族的耐性是
   46 秒——他一定會流失。改成耐性隨樓高放大（`× (1 + 樓層/45)`）。
   放棄率因此從 47% 掉到個位數。
2. **目的地控制／群組控制看不見「人數」。** 取樣乘客一個抵二十個，但權重算式只算「一個」，
   所以電梯永遠不去接那些價值 20 倍的呼叫。權重乘上 `p.w` 之後，
   買這兩個演算法才真的會去搶高樓層的生意。

**校準過程**：到達率常數 `RATE_PER_WEIGHT` 調了三次（0.019 → 0.010 → 0.0134 → 0.0080）。
中間發現尖峰窗的寫法是「開關」而不是「調變」——離峰會掉到 0.12，整棟樓的日均人流被吃掉
七倍。改成窗內 1.8、窗外最低 0.45 之後才對得上原本的手調數值。

### 5.5 入住率與口碑（10、11）實作紀錄（2026-09-04）

**10 入住率**：蓋好 ≠ 有人。每個樓層帶記「已招商幾層」，空樓層 `floorWeight` 回傳 0，
不產生乘客也不產生抽象收入；畫面上是灰的、有工地斜線。

- 招商成本 = 基數 × 租戶等級 × `1.038^已招商總數`。第一層 $106，第 100 層約 $4 萬，
  填滿 200 樓約 **$2000 萬** —— 是整棵現金升級樹（$189 萬）的十倍以上
- 加蓋 5 層附 **3 層錨定租戶**，剩下 2 層自己招。不然擴張成本變三倍，早期會卡死

**11 口碑迴圈**：評價現在也決定有多少人上門，★0 → ×0.80、★5 → ×1.50。
實測同一棟樓只改評價，人流 0.21 → 0.59 人/秒，**2.8 倍差距**。

**測試中被推翻的第一版設計**（值得記下來）：
我把三個懲罰疊在低評價上——票價低、人流少、**還會失去付過錢的租戶**。
機器人跑 75 分鐘卡在 25 樓、評價 1.0 上不去，因為修好服務要買井，
但錢都被「退租又重招」吃掉了。**那不是張力，是一個會自我強化的坑。**

改成階梯式之後才對：

| 評價 | 後果 |
|---|---|
| < 1.6 | 招不到新租戶（可逆，只擋成長，面板會說明原因） |
| < 1.0 | 現有租戶才開始搬走 |
| > 4.3 | 口碑免費幫你多租出一層 |

同一個機器人改完之後跑到 55 樓（原本 25），FIFO 從 59 分提前到 32 分。

### 5.6 突發事件重新設計（8）

原本的事件是「每 75 秒擲一次骰子」，玩家完全沒有輸入，只能被動反應。
討論過三個方向：

| | 方向 | 評語 |
|---|---|---|
| **A** | **事件變成租戶類型**：招商時選這層租給誰——會議中心（散場潮）、宴會廳（深夜爆量）、資料中心（幾乎沒人但單價高）。高爆量租戶單價高但難服務 | **選這個當主體。** 跟 10 入住率直接接起來：招商決定人流的**形狀**，不只是多少。不需要新分頁 |
| **B** | **技能樹買應付事件的工具**：提前預警、爆量票價加成、一鍵疏散模式、縮小規模 | **一起做。** 事件現在來得毫無徵兆，預警最有價值 |
| C | 玩家主動觸發：花錢辦活動製造爆量換取加成 | 暫緩——跟超速（4.4）的定位重疊，都是「主動玩換風險報酬」 |

**決定：做 A + B。**

**實作紀錄（2026-09-04）**

**A 租戶類型**：招商不再只是「租出去」，而是**選租給誰**。七個樓層帶共 16 種租戶，
各有自己的單價倍率、人流倍率與突發事件。平穩的租戶安靜，賺錢的租戶吵。

| 辦公層 20 層跑 400 秒 | 到達率 | 事件 | 組合 |
|---|---|---|---|
| 一般辦公 | 0.28 人/秒 | 無 | ×1.00 單價 |
| 會議中心 | 1.57 人/秒 | 每 44 秒一次散場 | ×1.55 單價 |
| 客服中心 | 1.87 人/秒 | 每 50 秒一次換班 | ×1.25 單價 ×1.60 人流 |
| 資料中心（實驗層） | 0.22 人/秒 | 無 | ×2.40 單價 ×0.25 人流 |

資料中心是刻意留的「喘口氣」選項：幾乎沒人搭電梯，但少數幾趟單價極高。

**B 三個藍圖技能**：人流預警（提前 8 秒／級預告，事件排隊等到期才湧出）、
尖峰加給（事件乘客票價 +18%／級）、疏散模式（一鍵把所有電梯調去爆量那層，
冷卻 90/70/50 秒）。實測按下疏散：五台車全部從 19 樓往 30 樓移動，
其中兩台沿路順便接客——這是對的電梯行為，不是 bug。

**測試中抓到三個 bug**

1. **錨定租戶把電影院租進辦公層**。`defaultTenant` 取「表上第一個符合這一帶的」，
   而電影院的 `bands` 同時包含 retail 與 office，剛好排在一般辦公前面。
   改成每一帶明確標 `plain:true`。
2. **口碑退租把整個樓層帶的租戶記錄清成 NaN**。退租的程式還在用舊的「數字」格式，
   `st.leased[band]--` 打在新的租戶物件上得到 NaN，`bandLeases` 判定不是物件就回傳空的，
   於是一次退租等於整帶清空。這是會**默默毀存檔**的那種 bug。
3. **事件頻率隨層數線性成長**，20 層會議中心變成每 9 秒一次散場。
   改成頻率溫和成長（`1 + 層數/8`）、規模跟著長（`1 + 層數/25`），現在是每 44 秒一次。
