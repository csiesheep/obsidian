## 四、電梯公司：詳細設計

### 4.1 為什麼這個點子好

三個結構性優勢：

1. **進度軸就是收入軸。** 樓層數同時是「你走多遠了」和「你賺多少錢」。大多數增量遊戲得硬把這兩件事綁在一起（Dirt Clicker 的地層得額外配掉寶表才有意義），電梯天生就綁好了：票價 = 樓層差。
2. **張力是內建的，不是外掛的。** 樓越高，單趟收入越高，但**往返時間也越長**，低樓層乘客等到不耐煩就走人。這不是設計師硬塞的限制器（像體力條），而是從題材本身長出來的兩難。這種張力玩家會覺得公平。
3. **視覺天生適合手機直式。** 垂直捲動的井道剖面填滿螢幕，往上蓋的時候相機拉遠、樓變成一根細長的塔——這個「看著自己蓋的東西變高」的畫面本身就是獎勵。

### 4.2 核心循環

```
乘客在某樓生成（有目的地、耐性條）
  → 玩家/演算法決定電梯下一站
    → 電梯移動（加速 → 巡航 → 減速）
      → 開門、上下客
        → 收入 = 基礎票價 × |樓層差| × 乘客倍率 × 滿意度乘數
          → 花錢升級 → 樓變高 → 流量變大 → 回到開頭
```

### 4.3 核心動詞：手動調度

早期完全手動。畫面上顯示各樓等待中的小人偶（頭上有目的地標籤），玩家**點擊要去的樓層**來調度電梯。

這比純點擊有腦，因為玩家實際上在做取捨：先接 3 樓那三個上班族（近、便宜、快沒耐性），還是衝去 28 樓接那個 CEO（遠、超高單價、耐性極低）？

而且自動化的路徑非常乾淨：你買的不是「自動點擊器」，是**更好的調度演算法**。

### 4.4 體力的對應物：馬達過熱

按住空白鍵／長按讓電梯超速行駛（1.8×），但熱量累積。過熱就強制停機冷卻 8 秒，期間所有乘客耐性照跑。

這給了主動遊玩一個持續的、有風險的操作，對應 Bills Must Be Paid 的體力機制，但不會硬性結束一局。升級路線：散熱片 → 液冷 → 超導馬達（過熱機制最終被移除，這本身就是一個爽的里程碑）。

### 4.5 貨幣

| 貨幣 | 用途 | 是否跨 Prestige |
|---|---|---|
| **現金 $** | 一般升級：速度、載重、門、電梯井 | ✗ |
| **藍圖 📐** | 技能樹、樓層類型解鎖、地基等級 | ✓ |
| **評價 ★** | 不是貨幣，是**乘數**。滿意度累積成大樓評價，評價高 → 更高單價的租戶入住 → 所有票價 ×N | 部分保留 |

評價是這個設計的第二個聰明處：它讓「別讓乘客生氣」有長期複利價值，而不只是當下少賺一筆。

### 4.6 核心數值

電梯只有五個屬性，全部互相牽制：

| 屬性 | 影響 | 取捨 |
|---|---|---|
| 巡航速度 | 長程變快 | 對短程幾乎無幫助 |
| 加速度 | 短程變快 | 對長程幾乎無幫助 |
| 載客量 | 一趟載更多 | 但上下客時間變長 |
| 開關門時間 | 每站省秒數 | 站數多才有價值 |
| 電梯井數 | 平行處理 | 成本最貴，且需要調度演算法才發揮 |

**這五個屬性沒有一個是「全面更好」的**，所以升級選單永遠是真決策。這是 Bills Must Be Paid 的鎚子系統（高爆擊小範圍 vs. 高速大範圍低傷害）的同一招。

### 4.7 起始平衡（第一版）

```
起始狀態
  樓層數：10
  電梯井：1
  巡航速度：1.0 樓/秒
  加速度：0.5 樓/秒²
  載客量：4
  開關門：2.0 秒
  乘客生成：每 4 秒 1 位

經濟
  票價 = $1 × |樓層差| × 乘客倍率 × 評價乘數
  成本曲線 = base × 1.12^已購買數

前三個升級（教學用）
  +2 載客量        $50
  開關門 -0.4 秒    $80
  +5 層樓          $200   ← 第一次感受到「樓高 = 錢多」
```

第一次自動化（自動關門）應該在**遊玩約 6 分鐘**出現，第一個完整調度演算法在 **15 分鐘**。太晚玩家會累。

### 4.8 自動化階梯

這是遊戲的骨幹，也是最有梗的部分——因為電梯調度是**真實存在的電腦科學問題**：

1. **自動關門** — 最基本的解放
2. **FIFO 調度** — 誰先按誰先服務。笨，但你不用點了
3. **SCAN 演算法** — 電梯掃到頂再掃到底，不折返
4. **LOOK 演算法** — 掃到最遠請求就折返，不跑空段
5. **目的地控制（Destination Dispatch）** — 乘客在大廳先輸入目的地，系統分組。真實高樓技術
6. **群組控制** — 多井協同，不再各自為政
7. **快速電梯（Shuttle）** — 只停高樓層，不吃低樓流量
8. **雙層轎廂（Double-decker）** — 一次服務兩層
9. **空中大廳（Sky Lobby）** — 真實摩天樓設計，換乘節點，讓超高樓在數學上可行

玩家在解鎖第 3 個之後會發現：**這些演算法真的有效率差異**，而且遊戲有統計頁面能看出來（借 Dirt Clicker 的「誰在偷懶」）。

### 4.9 乘客類型（收集要素）

| 類型 | 票價 | 耐性 | 特性 |
|---|---|---|---|
| 上班族 | 低 | 低 | 量最大，尖峰時段暴增 |
| 觀光客 | 中 | 高 | 拍照，拖慢開門 2 秒 |
| 送貨員 | 高 | 中 | 佔 2 格空間 |
| 保全 | 無 | ∞ | 不付錢，但提升評價 |
| CEO | 極高 | 極低 | 要求專用電梯，讓他等會扣評價 |
| 貓 | 無 | 高 | 純提升評價。稀有 |
| 幽靈 | ??? | — | 只在 13 樓出現。稀有掉落 |
| 搬家公司 | 極高 | 低 | 塞滿整台電梯 |

目標約 20 種，配一本圖鑑。這是獨立於數字線之外的獎勵管道。

### 4.10 樓層類型（進度軸）

| 樓層 | 類型 | 解鎖的東西 |
|---|---|---|
| 1–10 | 零售 | 基礎流量 |
| 11–30 | 辦公 | 尖峰時段機制（早上 9 點暴衝） |
| 31–60 | 飯店 | 行李（載重機制）、夜間流量 |
| 61–100 | 住宅 | 常客、寵物 |
| 101–150 | 觀景台 | 觀光客潮 |
| 151+ | 實驗樓層 | 破壞平衡的東西 |
| 終局 | 屋頂 → 軌道 | 電梯衝出大氣層，遊戲結束 |

**結局很重要。** 參考的三款都是短遊戲，目標總時長 **4–6 小時**。

### 4.11 Prestige：打掉重蓋

觸發條件：蓋滿一定樓層或收入達標。

**保留**：藍圖、已解鎖樓層類型、乘客圖鑑、地基等級（= 新樓的基礎速度與最大高度）
**歸零**：現金、樓層數、所有現金升級

```
藍圖獲得量 ≈ floor( sqrt( 本輪總收入 / 1e6 ) )
```

主題上完美：拆一棟樓蓋更高的一棟，正是現實摩天樓的歷史。

技能樹三大分支：

- **機械**：速度、加速、載重、散熱
- **營運**：調度演算法、多井、群組控制
- **建築**：起始樓層、樓層類型、空中大廳

### 4.12 UI 與視覺

- **手機直式（主要）**：井道剖面填滿螢幕，升級用底部抽屜（swipe up）
- **桌機**：左側井道，右側升級面板
- 美術風格：扁平向量或像素，樓層有不同配色與家具剪影
- 乘客是小人偶，頭上有目的地數字標籤，耐性用頭頂細條表示（快沒耐性時變紅並晃動）
- **關鍵爽點**：每次增加樓層，相機平滑拉遠。玩到後期整棟樓縮成一根細塔，你能一眼看到自己蓋了多高
- 音效：叮！開門聲、樓層播報。這遊戲的音效設計空間很大且很便宜

### 4.13 技術注意事項

- 電梯運動是**簡單 1D 運動學**（等加速 → 巡航 → 等減速），不需要物理引擎。約 40 行程式碼
- 乘客是純物件陣列：`{ id, origin, dest, type, spawnTime, patience }`
- **最大的技術決策**：後期樓層數上百、乘客數上千，逐一模擬會爆。必須在中期切換成**統計流量模型**——高樓層不再逐個模擬乘客，改用「該區段每秒產生 N 元」的抽象。**這件事要在第 3 週前就決定好架構**，事後補很痛
- 離線收益：用平均流量 × 時間直接算，**不要重跑模擬**
- 存檔大小要注意：不要把乘客陣列存進 localStorage，只存統計數字

### 4.14 已知風險

| 風險 | 對策 |
|---|---|
| 手動調度太忙會累人 | 自動化提早，第一個演算法 15 分鐘內給 |
| 「進度軸就是錢」導致低樓層迅速失去價值，玩家只跑頂層 | 低樓層流量隨大樓高度**同步成長**（住戶都要經過大廳），並讓零售層有獨立的評價貢獻 |
| 五屬性互相牽制聽起來好，但可能算不出最佳解而讓玩家癱瘓 | 提供一個「效率」統計數字（每分鐘樓層數 × 載客率），讓玩家有可比較的單一指標 |
| 演算法梗太宅 | 每個演算法配一句白話說明 + 一個能看出差別的動畫示意 |

### 4.15 第一個原型該做什麼

**兩天內做完，只做這些：**

- 一個 10 層的井道，SVG 或 canvas
- 一部會動的電梯（加速度運動學）
- 點樓層 → 電梯過去 → 開門 → 上下客 → 加錢
- 乘客每 4 秒生成一個，頭上有目的地數字
- 一個計數器顯示 $

**驗證問題**：光是「點樓層、看電梯滑過去、叮一聲開門、錢跳出來」這件事，有沒有讓你想再點一次？

有的話，其他所有系統都值得做。沒有的話，問題在動詞的手感（速度曲線、音效、開門動畫），先修那個，不要急著加升級。

### 5.1 診斷：一行 clamp 造成的三個症狀

`js/sim.js` 的 `spawn()` 裡：

```js
const top = Math.min(st.floors, C.SIM_FLOORS);   // SIM_FLOORS = 40
```

| 症狀 | 原因 |
|---|---|
| 電梯永遠在低樓層往返 | 200 層的樓，**看得見的乘客只生成在 1–40 樓**，上面 160 層一個人都沒有 |
| 高樓層沒有客人 | 同上；4.13 的統計流量模型把他們變成了看不見的數字 |
| 蓋高樓沒有變忙 | `spawnEvery`（`js/state.js`）用同一個 clamp → **超過 40 樓之後人流不再增加** |

1–40 樓之內是**均勻分布**外加 15–45% 的大廳偏好，沒有任何真實建築的垂直人口結構。

這同時也是「後期沒事做」的根因：**後期的人全部住在玩家看不到的抽象模型裡。**

順帶量出來的平衡問題（2026-09-04）：

- 所有現金升級買滿只要 **約 $189 萬**，而後期收入約 **$336 萬/分** → 現金樹撐不到一分鐘
- 藍圖全樹＋全自動化只要 **471 📐**，一輪 100 億收入給 100 📐 → 約 5–8 次拆樓就全滿
- **整個遊戲沒有任何無上限的 sink**，每一項都有 max，而那些 max 相對後期收入小到可以忽略

### 5.2 人流與樓層：12 個點子

✅ = 這一輪選定實作。

**樓層分布**

**1. ✅ 取樣模擬（sampled simulation）** — 核心
高樓層不是不生成人，而是**只生成 5%，每個人身上帶 20 人份的票價**。畫面上高樓層有零星但高價的乘客，電梯有理由跑上去，CPU 仍是常數級。沒有推翻 4.13 的決定，只是把「不模擬」改成「抽樣」。
> 抽象收入要扣掉被取樣出去的那一部分，否則重複計算。

**2. ✅ 垂直人口分布（OD matrix）** — 丟掉 uniform
每個樓層帶有自己的起訖傾向：大廳約 40% 起訖、辦公層早上進晚上出、住宅層相反、飯店層夜間到達、觀景台單向朝聖。真實電梯交通研究就是用 OD matrix 算的，順便把行程長度拉開。

**3. 手扶梯／低區獨立電梯**
花錢把 1–5 樓的人流從電梯移走（真實建築就是這樣做的）。**用錢買清淨**，買下去之後剩下的都是長程高價客。同時是後期的現金 sink。

**4. 空中大廳變成真的轉運點**
現在 sky lobby 只是個倍率。改成真的兩段式行程：低區車只到大廳，高區車從大廳往上。高樓層自然有車在跑，而且「換乘」本身是新的調度難題。

**5. 頂樓吸引子**
觀景台／婚宴廳／直升機坪＝目的地磁鐵，製造穩定的長程高價流。13 樓的幽靈已證明「某層有特別的東西」很有記憶點。

**6. ✅ 解除 `spawnEvery` 的 clamp**
用真實樓數而不是 `min(floors, 40)`，人流才會隨大樓成長。
> 單獨做這條會直接把低樓層淹掉，**必須跟 1 一起做**。

**客人數量**

**7. ✅ Poisson + 「今日人潮」隨機遊走**
現在是固定間隔的節拍器。改成 Poisson 分布，再乘一條緩慢隨機遊走的日係數。平均值一樣，體感天差地遠——有忙到爆的時候，也有喘息的時候。投報率最高的一條。

**8. ✅ 突發流量事件**
會議散場、火警演習、演唱會散場、跨年倒數：一次在同一層丟出 20 個人。這是唯一會讓玩家「啊糟糕」然後手動接管的東西，也是後期還會主動玩的理由。

**9. ✅ 一週作息**
平日／週末不同曲線，而且飯店層與辦公層**相反**。一天 3 分鐘 → 一週 21 分鐘，剛好是一個 session 的長度。

**10. 入住率（Occupancy）**
樓蓋好不等於有人，要花錢招商。同時解決三件事：高樓層為什麼沒人、現金沒有 sink、以及「蓋新的 vs 填滿舊的」變成決策。

**11. 口碑迴圈**
評價目前只影響票價。讓它也影響**人數**：高評價 → 更多人 → 更忙 → 更容易失控。評價變成真正的雙面刃。

**12. 天氣與災害**
颱風天人少但耐性差；停電只剩一台能跑；地震後全部停機檢查。讓多買的那幾座井有「冗餘」的意義。

### 5.3 後期成長：15 個點子

後期真正缺的不是數字，是「有事情要決定」。純粹再加「+5% 速度」只會讓一個沒有互動的畫面數字變大。

**A. 止血（純資料改動，最快）**

1. **Mk II 無限升級** — 買滿的升級轉成無限等級版（+3% 乘法／級，成本成長 ×1.4）。現金終於有無底洞
2. **里程碑倍率** — 每 25 樓永久 ×1.15 收入，200 樓不再是一面平的牆
3. **藍圖來源多元化** — 成就、圖鑑集滿、每個樓層帶首次解鎖都給 📐，不要只靠 `sqrt(收入)` 一條管道
4. **評價開上限** — ★5 之後進入「聲望」，每 0.1 給票價加成，遞減但無上限

**B. 讓後期有決策（重點）**

5. **分區服務 Zoning** — 手動指定每座井的服務樓層區間（低／中／高區）。真實摩天樓就是這樣配的，而且樓每長高一段就要重解一次
6. **可調參數的調度器** — 把 dispatcher 的權重開成滑桿：等待時間 vs 距離 vs 票價 vs 耐性，統計頁即時顯示效率。**零內容成本、無限優化深度**，完全切中主題
7. **時段策略** — 早上上行尖峰、傍晚下行尖峰要用不同編組，真實電梯控制系統本來就有這個模式

### 5.6 突發事件重新設計（8）

原本的事件是「每 75 秒擲一次骰子」，玩家完全沒有輸入，只能被動反應。
討論過三個方向：

| | 方向 | 評語 |
|---|---|---|
| **A** | **事件變成租戶類型**：招商時選這層租給誰——會議中心（散場潮）、宴會廳（深夜爆量）、資料中心（幾乎沒人但單價高）。高爆量租戶單價高但難服務 | **選這個當主體。** 跟 10 入住率直接接起來：招商決定人流的**形狀**，不只是多少。不需要新分頁 |

**實作紀錄（2026-09-04）**

**A 租戶類型**：招商不再只是「租出去」，而是**選租給誰**。七個樓層帶共 16 種租戶，
各有自己的單價倍率、人流倍率與突發事件。平穩的租戶安靜，賺錢的租戶吵。

| 一般辦公 | 0.28 人/秒 | 無 | ×1.00 單價 |

**B 三個藍圖技能**：人流預警（提前 8 秒／級預告，事件排隊等到期才湧出）、

**測試中抓到三個 bug**

1. **錨定租戶把電影院租進辦公層**。`defaultTenant` 取「表上第一個符合這一帶的」，
   而電影院的 `bands` 同時包含 retail 與 office，剛好排在一般辦公前面。
   改成每一帶明確標 `plain:true`。
2. **口碑退租把整個樓層帶的租戶記錄清成 NaN**。退租的程式還在用舊的「數字」格式，

3. **事件頻率隨層數線性成長**，20 層會議中心變成每 9 秒一次散場。

**拿掉抽象層之後，才發現它一直在偷偷付錢。** 全自動後期收入從 $4.2k/秒掉到 $522/秒，
機器人卡在 25–40 樓、120 分鐘只賺 $2.2 萬。抽象層不只是「高樓層的替身」，
它是後期收入的主要來源，而且是不受電梯吞吐量限制的那一種。

兩個補償：
1. **租戶等級曲線變陡**（頂端 14 → 42）——樓高改成「每一趟更值錢」，而不是「更多趟」
2. **到達率改成次線性**（`RATE_PER_WEIGHT 0.032 × 權重^0.5`）——樓高買到的是單價，不是流量

招商成本也要跟租戶等級脫鉤（改用 `sqrt(tier)`），否則頂端 42 倍的等級會讓招商貴到不合理。

**真正的坑是評價死亡螺旋。** 三次自動測試裡有一次直接卡死：15 樓、90 分鐘、收入完全沒動。
原因是評價的三條線：`RATING_MIN` 0.8 < `CHURN_RATING` 1.0 < `LEASE_BLOCK` 1.6，
**中間 1.0～1.6 是死區**——租戶不會再來（招商鎖住），但也還沒差到會退租（需求不會下降），
收入停在原地，於是永遠買不起第二座井。200 樓版有抽象層的被動收入把你拖出來，拿掉之後就沒有回復力了。

修法：加一條單向的「爛評價會過期」回穩項——低於 2.0 時評價自己往回爬（每秒趨近 1%），
但**不往下拉**，五星是玩家自己掙來的，不該被平均值吃掉。改完三次測試曲線一致，不再卡死。

**結局價碼重新校準。** 原本的 $5 億是照 200 樓版訂的，而且要在**單一輪**內存到（拆樓會歸零）。
實測 16 輪、技能 71/83，峰值現金只有 $6M——這個結局是死內容。抽成 `ORBIT_CASH` 常數並改成 **$20M**：
機器人買齊藍圖階調度（目的地／群組／快速／雙層／空中大廳，共 38 📐）之後，
實測在**第 19 輪第 83 分**達成，當時技能樹 77/83、藍圖 30 張、末段收入約 $4.6k/秒。
> 順帶一提：我第一次量到「後期收入卡在 $2–4k/秒」是因為機器人根本沒買藍圖階的調度。
> 補上之後收入持續成長，5.3 的「後期沒有無上限 sink」仍然成立，但沒有原本量到的那麼嚴重。

**順手清掉的死碼**：取樣乘客（`p.w` 恆等於 1）的整套繪製、`×20` 標記、HUD 的「高樓 N」計數、

### 5.9 天空、中式屋頂、室內設計（2026-09-04）

四件事一起做：取消黑白切換改成時間驅動、真的天空與日月、pixel-art 中式屋頂、
每個樓層帶的室內。設計稿在 `design/`：Tower（主稿）、DirectionB、Sky、Roof、Interiors。

**版面的取捨（方向 A：天際線）。** 以前大樓是滿版剖面，從 `pad` 畫到 `W - pad`，
左右不留一點空，所以沒有地方放天空。方向 A 讓出左右各 62px、上方讓出屋頂與一條天空、
下方讓出街道。實測代價比預估小：100 層時每層從 3.72px 降到 **3.4px**（原本估 2.8px）。
方向 B（滿版剖面、天空只佔頂端一條）也畫了稿，代價是日月走不出弧線。

**做的時候撞到四個問題**

1. **太陽在正午整個躲在大樓後面。** 弧線的峰值還落在樓身範圍內，等於沒有「日月隨時間變化」
   這件事。上方要留一條真的天空（`skyTop`），弧線峰值才進得去。
2. **`roofHeight` 算反了。** 高度是「格數 × 格寬」算出來的，而小屋頂的格數少（21 vs 49）、
   每格反而更大，結果 100 層的屋頂比 14 層的還高。高度必須跟格寬脫鉤。
3. **翼角在扁屋頂下斷成飄空的碎塊。** 原本用 `flick`（在屋簷之上補幾筆）做翹角，
   水平跳距在正常比例下只有幾 px，屋頂一壓扁就變成一百多 px 的斷口。
   改成正統做法：屋簷下緣在末端往上抬，**每格只抬一階、厚度固定兩格**，這樣一定連得起來。
4. **夜裡整棟樓變成一塊黑板子。** 真實的大樓正好相反，天越黑它越亮。
   室內的重點色在夜裡轉成暖燈色（`winLit`），窗戶就亮了。

**一個推翻了原始想法的發現：介面不能跟著做整套亮暗翻轉。**

原本的計畫是「介面的 CSS 變數也要跟著時間走，否則畫布是黃昏、面板還停在深夜」。
實作完才發現這是錯的，兩個理由：

- 深色與淺色兩套 UI 做**線性插值，文字和背景會在中點相遇**——對比歸零，
  整個面板褪成灰白、字讀不到。日夜交界每一次都會經過那個中點。
- 就算解決了對比，**一天只有 180 秒**，介面每 90 秒亮暗翻一次是災難。

所以：完整的日夜交給畫布（那是世界），介面只在深色系裡漂移——白天亮一階、暖一點，
夜裡沉下來、偏冷，文字永遠是淺色。原本的亮色 UI 主題等於退役了。

**室內設計的誠實話**：它是前中期的獎勵，不是全程的。100 層時每層只有 3.4px，
什麼家具都畫不下。以前只有一個門檻（`detail = fh >= 16`）過了就整個消失；
改成四段階梯——完整家具（fh≥24）、小家具（fh≥14）、窗戶簽名（fh≥8）、只剩色條。

**使用者中途改的一項**：屋頂高度降到 1/3、寬度蓋滿整個大樓。
比較像 圓山那種寬而低的大屋頂，不是頂上的小亭子。


### 5.10 五個屋頂（2026-09-04）

原本那個中式屋頂佔的高度太多、也不好看。砍一半（23px → **12px**）並重新設計五種樣式：
中式歇山頂、古羅馬山牆、裝飾藝術階梯冠、哥德尖塔群、伊斯蘭圓頂。
**樓體完全不變**——五個共用同一個高度與寬度，換屋頂只換 `drawRoof` 畫的東西。

**技術上換了做法：粗格子 → 1px 逐欄剖面。**
屋頂 12px 高、500px 寬是 38:1 的長條。原本 49×12 的手排格子在這個比例下，
每一格會被拉成 10×1 的色帶——那不是像素藝術。改成每一欄自己算上下緣，
畫出來的每個點就是螢幕上真的一個像素，曲線（反宇、圓頂）才有機會成立。

**唯一畫壞的地方：重複件的間距寫死了像素數。** 斗拱每 7px、拱廊每 11px——
在 200px 寬的屋頂上剛好，在 500px 寬的屋頂上全部糊成一排梳齒。
改成「屋頂寬度的幾分之一」（斗拱 W/26、城垛 W/16、拱廊 W/15…）之後才成立。

其他兩個修正：古羅馬的山牆拉滿寬會變成 40:1 的斜坡（不像神廟像屋簷），
改成只佔中央 48%、兩側是女兒牆；伊斯蘭的拱洞開太大，柱墩細到不見，整排讀成黑色水滴。

**出貨方式**：五個都留，玩家在「升級」分頁自己選，存進存檔、跨拆樓保留、純外觀不影響數值。

**順手修好一個一直在騙人的東西**：`python -m http.server` 不送 `Cache-Control`，
瀏覽器會把 ES module 快取住——改了檔案、重新整理、開新分頁都還是舊的程式。
這次因為看到「存檔欄位加了但讀不到」才發現。開發用的伺服器換成會送 `no-store` 的版本。


### 5.11 拆樓頁：拿掉門檻、把說明從按鈕變回說明（2026-09-04）

兩件小事，但第二件是一個一直在誤導人的介面問題。

**拿掉門檻。** 原本要 40 層樓（`PRESTIGE_FLOOR`）而且至少換得到 1 張藍圖才准拆。
現在隨時都能拆，藍圖是 0 的時候只提醒「現在拆掉等於白拆一次」，不擋。
`PRESTIGE_FLOOR` 與 `canPrestige()` 整個移除。

**「保留／歸零」本來長得就是按鈕。** 它們用的是 `.card`——跟購買鍵完全同一個
class，同樣的 3px 邊框、4px 硬陰影、hover 變色、`cursor:pointer`。那是說明文字，
不是可以按的東西。改成兩欄清單（`.ledger`）：沒有邊框、沒有陰影、沒有 hover，
只在標題前放一個 7px 的色塊（綠＝保留、紅＝歸零）。

順手修了一個 user-facing 的錯誤：拆樓頁顯示的公式寫死「√(本輪收入 ÷ 100萬)」，
但 `PRESTIGE_DIV` 在 5.7 就改成 1 萬了——差 100 倍。改成吃常數當參數。

清單內容也對齊了實際行為：保留那欄補上「屋頂樣式」（5.10 之後它跨拆樓保留），
歸零那欄補上「招商與租戶」「評價」（`newGame()` 確實會重設這兩個）。

「清空存檔」也從升級頁搬到拆樓頁。它放在升級頁很怪——那一頁其他每一張卡
都是花錢買東西；跟「拆掉重蓋」放在一起才對，兩個都是重來，只差重來多少。


### 5.12 畫面上的三個數字（2026-09-05）

樓層號、等待乘客的目的地、轎廂裡的目的地都太小看不清楚。量過之後，問題不只是「小」：

| | 原本 | 可用空間 | 診斷 |
|---|---|---|---|
| 樓層號 | 11px system-ui | 整層樓寬 | 純粹太小 |
| 等待乘客 | 9px | 每人 19px | 太小，**而且畫在 `y+10`＝樓層下緣外 3px**，其實壓在下一層樓上 |
| 轎廂內 | 9px | **每人 6.1px** | 任何字型都塞不下——四個數字是疊在一起的 |

**先換字，不是調大小。** 遊戲是像素風，system-ui 在 9–11px 會被反鋸齒糊成一團灰。
3×5 點陣字放大兩倍（6×10px）比 11px 系統字還好認，每個點都落在整數像素上。→ `js/digits.js`

**樓層號**：點陣字 + 底板（沒底板會跟室內家具疊在一起），fh≥24 用 ×3、fh≥13 用 ×2。

**等待乘客**：牌子從腳下移到<b>小人右邊、垂直置中</b>。垂直方向真的沒空間——樓層 26px 高，
小人就佔 18px。代價是每人 19px → 33px，但本來就最多畫 6 個人、一層放得下 9 個位置，沒有損失。

> 補（同日）：隊伍原本從左邊排起，第一個人的牌子會緊貼左緣的樓層號。改成
> <b>靠著電梯、由右往左排</b>——排隊的人本來就該在門口，而且樓層號那一側直接淨空。
> 「+N」也跟著移到隊尾（左端）而不是門口。人數條（fh 太小、畫不出人的時候）同方向處理。
> 樓層號牌子的右緣抽成 `numLeft(fh)`，畫號碼跟排隊共用，不會各算各的。

**轎廂：顯示隨遊戲階段變（使用者的設計，比我提的兩個方案都好）**

- 手動期（`isManual()`：還沒有任何調度演算法）：只顯示<b>要去哪些樓層</b>，去重、由小排到大，
  不畫乘客。那是你決定下一個點哪層的依據。井道加寬（每座 30px → 60px）才排得下。
- 有調度演算法之後：那些數字是雜訊，改回畫乘客，井道縮回去，樓層拿回寬度。
- `isManual()` 放在 `state.js`，跟 `sim.js` 的 `nextTarget()` 用同一個條件——不能各寫各的。

> 補（同日）：第一版是固定字級、放不下就 `+N` 截斷。但手動期少看到一個目的地就是漏一趟，
> 所以改成 <b>從大到小試字級，挑第一個裝得下全部的</b>——車上人少就大大地寫，人多就縮小，但不省略。
> 井道寬度也跟著<b>載客量</b>算（不是跟著當下車上幾個人：那樣每次有人上下車版面就會抖，比截斷還糟）。
> 掃過 ~150 種「樓層數 × 載客量 × 井數」的組合，只剩 4 組會截斷，全是同一個形狀：
> 20–22 樓 × 3 座井 × 高載客量 × 還沒買調度演算法，此時井道撞到「最多佔 60%」的上限，差 1–3 格。
> 三座井要 $1,400+$2,730+$5,300，FIFO 只要 $450——沒有人會走到那個狀態。
>
> 再補：一開始我把同樓層去重了，但那會把「兩個人都要去 9 樓」壓成一個 9——
> 看不出車上有幾個人、也看不出哪一層下得多。改成 <b>一位乘客一個數字</b>，
> 重複的樓層重複出現，數字的個數就等於車上人數。
> 上限也跟著從「相異樓層數」變成<b>載客量</b>。
> 井道寬度的上限維持在畫面的 60%：試過放寬到 66%，三座井 + 高載客量時樓層只剩 152px、
> 被井道擠掉三分之二——那比截斷還糟。
> 重掃 189 種組合：<b>一座井與兩座井零截斷</b>，剩下 13 組全是三座井 + 載客量 ≥20 的組合。

**兩個實作時撞到的東西**：

1. 第一版把數字連著放、間距 3px，「1 3 5 8」讀成「1358」，兩位數更糟。改成<b>網格</b>：
   每格固定兩位數的寬度、靠右對齊、間距 6px。
2. 加寬井道原本只看 `isManual`，結果 100 層手動時井道也被撐寬——但那個高度（每層 3.7px）
   根本畫不出數字，等於白白吃掉樓層寬度。加寬要跟「畫得出數字」綁在一起（`fh >= 16`）。


### 5.13 室內配色：背景退後，乘客和數字站出來（2026-09-05）

原始需求是「室內背景太搶眼，乘客和數字比較重要；而且乘客和數字不該隨日出日落改變顏色」。
把四個時刻並排畫出來之後，發現問題比這個更嚴重一層。

**現況在黃昏和天微亮時，乘客和數字幾乎看不見。** 不是「不夠突出」——樓層底色的乘數
從夜 0.40–0.50 盪到日 1.72–1.95（近四倍），而小人的墨色從 `#cfd6e6` 翻到 `#16183a`。
日夜交界時兩邊**同時走到中間灰**，對比直接歸零。
> 這跟 5.9 在介面 CSS 變數上撞到的是同一個病：兩端都會翻的東西做線性插值，中點必然相遇。
> 上次的結論是「介面不要翻」，這次是「背景不要翻」——同一個教訓的第二次。

**所以那兩件事其實是同一件事**：墨色之所以要翻，正是因為背景會翻。要讓乘客和數字固定，
背景就得留在一個窄的範圍裡——而那剛好就是「別那麼搶眼」。

**新規則：室外隨時間變，室內不變。**

| | 現況（夜 → 日） | 改成 |
|---|---|---|
| 樓層底色乘數 | 0.40–0.50 → 1.72–1.95 | 0.52–0.62 → 0.66–0.78（1.26 倍） |
| 家具 / 左緣色條 | 1.95 → 0.78 / 2.05 → 1.15 | 1.42 / 2.30 固定 |
| 乘客墨色 | #cfd6e6 → #16183a | #eaf0fb 固定 |
| 轎廂內裝 / 車內墨色 | #20242e → #eef3fb | #e6ecf7 / #12161f 固定 |
| 數字底板 / 墨色 | #0e1119 → #f2f4fa | #0d1018 / #c8d0e4 固定 |
| 井道、空樓層、耐性條、人數條 | 都在翻 | 全部固定 |
| 天空、街道、外牆、屋頂、遠景 | 隨時間 | **不變，照舊隨時間** |
| 窗戶的燈（winLit） | 夜裡轉暖 | **不變**——這是唯一該隨時間變的室內元素 |

論證上也站得住：大樓內部是人工照明的，正午和晚上八點的辦公室看起來差不多。
日夜交給天空、街道、外牆和窗戶的燈去表達。

使用者選了「留一點」而不是「完全不變」：底色還是有 1.26 倍的擺盪，盯著看得出來，
但壓不過前景。

**驗證**：四個時刻取樣，`ink` / `numPlate` / `car` 三個值完全相同，`floorA` 只在
0.62–0.78 之間動，而 `ground` / `far` 照常全幅變化。兩張色表各 52 個鍵、集合完全一致
（不一致的話 `blend()` 會產生 undefined，而且不會拋錯）。
