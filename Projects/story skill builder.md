# story skill builder

一個 Claude Code skill，帶著一個 session 把「某一類短文的產生器」做成像 [[ghost story generator]] 那樣的 skill：資料驅動的骨架表、從資料推出的寫作規則、自我檢查標準、校準過的兩兩評審，最後包成 `csiesheep/skills` 的一個目錄並測試。它自己不產生故事，它產生「產生器 skill」。

2026-10-16 擬，同日拍板名字 `story-skill-builder`，先把鬼故事管線程式搬進 repo。

## 共用的部分（所有類型不變）

| 共用的部分 | 內容 |
|---|---|
| 流程 | 定義 → 找來源 → 抓取 → 整語料 → 標註 → 統計 → 規則 → 產生器 → 評審校準 → 盲測 → 包裝 → 測試 |
| 產物的形狀 | `SKILL.md`、`scripts/plan.py`（只用標準函式庫、抽骨架）、`assets/table.json`（去識別化）、`references/`（寫作規則、風格、自我檢查、兩兩評審、資料發現） |
| 程式 | PTT 抓取（看板、搜尋、精華區）、去重與系列合併、`claude -p` 標註（JSON schema、多執行緒、重試、記錄實際模型和成本）、同標籤同年份百分位、高低分組對比和 p 值、權重、評審校準、A/B 盲讀頁 |
| 教訓 | 絕對分數評審等於擲銅板，兩兩比較才有用，而且要在真實配對上校準過才能用；受歡迎不等於好（推文數要配第二個訊號，像毛率）；資料和擁有者的口味可能不同，兩種都留；資料公開前要去掉標題、作者、ID、網址 |

## 每個類型要決定的事（genre.json）

| 欄位 | 鬼故事 | 笑話（候選） | 心靈雞湯（候選） |
|---|---|---|---|
| 單位 | 一篇文，系列合併 | 一則笑話；轉錄文要去重 | 一篇文或一段語錄 |
| 來源與訊號 | PTT marvel，推文 | PTT joke、StupidClown，推文；Dcard 有趣（讚） | PTT share、Dcard 心情；訊號弱 |
| 標註軸 | 場景、機制、結尾、鬼的露出、節拍比例、字數 | 形式、笑點機制、題材、鋪陳與笑點比例、冒犯程度上限、結尾 | 主題、結構、修辭、說教程度上限、結尾 |
| 第二訊號 | 「毛」「雞皮疙瘩」vs「虛」 | 「XD」「笑死」vs「冷」「老梗」 | 「哭了」「需要這篇」vs「說教」「廢話」 |
| 口味 | 直接、留白 | 冷、鬧 | 溫、狠 |
| 規則底線 | 虛構、不點名真實地點 | 不針對族群、不用真實的人 | 不給醫療或財務建議 |

每個類型都要定義一個「露出上限」的對應物（冒犯程度、說教程度），那是鬼故事裡最有用的約束。

## 七個階段和關卡

1. 定義：類型、什麼叫好、給誰看、使用者喜歡的例子。產出 genre.json 草稿。關卡：使用者認可標註軸。
2. 來源與抓取：至少 1000 個有接收訊號的單位。PTT 看板用共用抓取器；其他來源先估可行性。關卡：回報數量和年份範圍。
3. 標註：先標 60 篇看分布，再估全量成本和時間。關卡：使用者同意花費。
4. 統計與規則：高低分組對比，規則 v1 每條附資料依據；算第二訊號。
5. 產生器與評審：抽骨架、寫手規則、自我檢查、兩兩評審。評審在真實配對上校準，低於 85% 不接進流程。關卡：回報校準數字。
6. 盲測與口味：使用者盲讀 A/B，決定留幾種口味。關卡：使用者選。
7. 包裝：建目錄、去識別化、README 加一列、測試、有 skill 和沒 skill 用兩兩評審比、開 PR。

## 訊號弱的類型

心靈雞湯最好的來源（FB 粉專、Threads）不能抓。要有「口味模式」：使用者自己評 100 篇或兩兩選 50 對，取代推文當訊號。產生器形狀不變，只是權重來自使用者而不是群眾，`findings.md` 要寫明。

## 估算

PTT 來源抓一萬篇約半天；標註每千篇 Opus 5.5 約 55 美元（鬼故事平均一篇 1500 字，笑話約五分之一）；鬼故事從零到 skill 三天的 session，有 builder 之後 PTT 來源的類型目標一天。
